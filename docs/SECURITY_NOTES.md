# Security notes and checkpoint scope

This is a student lab prototype, not a production lock, identity proof or safety system. The current v2 delivery stops at M2. Strict transaction-to-removal reconciliation, online item registry/levels, TTL/multiple sessions and upgraded vision remain pending.

1. **Cloned UIDs:** RFID UIDs can be copied. FNV-1a is a compact identifier, not encryption, a password or collision-resistant authentication. Duplicate hashes are refused on cache upload; active badges still need physical control.
2. **Serial spoofing:** WL CRC detects accidental corruption only. Anyone controlling the USB serial link can send AUTH, replace the cache or stop an alarm. Protect the laptop/USB cable and admin access. No cryptographic serial challenge/response is implemented.
3. **Replay:** OFF is at-least-once. The PC commits a unique (BOARD_ID, boot id, event id) row before OFFOK. Reused identity with a different hash/event is rejected. A two-slot boot counter survives a torn counter update. Replacing a board or fully erasing EEPROM while keeping old history requires a fresh BOARD_ID or a backed-up/new database; do not disable deduplication to hide a conflict.
4. **Offline limits:** At most 100 entries, eight badge identities and 16 pending records. A full log refuses new offline operations instead of overwriting history. Offline item ISS is not a loan ledger/return transaction. Power loss or board reset clears RAM sessions/logs; it preserves a valid EEPROM whitelist. Opening a UNO serial port may reset it, so test heartbeat loss while keeping the port open. Offline shelf removals are not detected.
5. **Revocation:** The previous valid whitelist survives an invalid/interrupted upload. That is safer than accepting partial entries, but means a revoked tag remains valid offline until the replacement commits. Wait for CURRENT/WLOK; inspect FAILED/BUSY diagnostics. M2 sync contains active personnel at level 1 only, pending the M3 item/clearance schema.
6. **Tailgating and stale sessions:** v1 policy still runs online at this checkpoint. A session is not proof that the person removing an item is its owner. M3/M4 must add TTLs, multi-session attribution and declared-versus-observed reconciliation. Person detection is a future optional aid with false positives, not a guarantee.
7. **Marker spoofing:** A marker can be detached or copied, and lighting/occlusion can fool empty-reference heuristics. Reveal markers, anchor rectification and learned positions are M6 work. Preserve physical marker-to-item attachment and calibrate the current v1 pipeline before using it even for a demo.
8. **Privacy:** Obtain consent for gate photos. Keep .env, camera URLs with credentials, images, databases, phone numbers and raw logs private. Share only redacted results. Use retention/Keep deliberately and back up before changing schema. Telegram tokens/chat IDs are not needed until M5; do not post them into code or chat.
9. **Buttons and watchdog:** A physical long press can silence an alarm if BTN_ACK_ENABLED=1; disable that option if unrestricted button access is inappropriate. Short mute suppresses sound, not visual alarm/history. A watchdog catches a hung loop, not a malicious or logically wrong program; old bootloaders require physical validation.

Alarm feedback and PW escalation stay on the UNO. Tests inject database, camera and notifier failures to verify dispatch isolation; inability to observe a new shelf event with failed cameras is a limitation, not a reason to invent a detection.
