# Decisions

1. Build at the existing repository root (`D:/inventorySystem`), rather than nesting another repository.
2. Python 3.11 is the supported development runtime (installed locally); Python 3.14 is not used because pinned OpenCV wheels target earlier runtimes.
3. A single FastAPI process owns hardware. Never run multiple Uvicorn workers. SQLite uses WAL, a busy timeout, and short per-operation sessions.
4. UNO owns all buzzer decisions. Serial authentication is sent before database event insertion or camera work. Notification and evidence queues run independently.
5. Simulation uses the real vision pipeline and a clock-injected firmware port; it never claims to measure electrical latency.
6. Demo data is created only in simulation or via the explicit seed command. Blank real installations start without authorized cards.
7. Official references checked on 2026-10-24: [MFRC522](https://github.com/miguelbalboa/rfid), [OpenCV](https://docs.opencv.org/4.x/d5/dae/tutorial_aruco_detection.html), [Twilio request validation](https://www.twilio.com/docs/usage/security), [Twilio 63016](https://www.twilio.com/docs/api/errors/63016). New OpenCV uses ArucoDetector/generateImageMarker; compatibility branches support detectMarkers/drawMarker. Twilio error 63016 means outside the 24-hour service window; this course project uses free-form sandbox messages, not template campaigns.
8. DevRelay community searches and event lookup were attempted but refused because the account is not connected. No community claims or links are fabricated.
9. UI uses React 18 and plain CSS, with the shelf feed as the primary control-desk view. The Vite pin was raised from 6.3.5 to 6.4.5 after npm audit reported advisories; the updated audit reports zero vulnerabilities.
10. Password, cookie secret and media HMAC secret are required in real mode and generated only into .env by the local setup script. Simulation without .env accepts an empty password on loopback for immediate exploration; it uses ephemeral signing keys. Never expose that unconfigured simulation publicly.
11. Notification request pacing also respects Twilio's documented sandbox limit of one message every three seconds; the worker spaces SDK calls by at least 3.1 s. The per-kind 20 s suppression is separate. Approved template messaging outside the service window is deliberately out of scope.
12. Gate incident evidence association runs before and independently of notification processing. An expired WhatsApp window cannot prevent storing or displaying a gate incident photo.
13. The camera ring retains at most five seconds. Clips resample to six seconds around an incident, duplicating nearest available frames if startup/history/network gaps leave insufficient coverage. Codec failure yields individually hashed JPEG frames. Real pre-event coverage depends on the source running before the event.
14. All secrets and connection credentials stay in .env. The settings table exposes nonsecret defaults, including serial/camera options. Serial/camera source and capture-rate changes require restart. Camera URLs containing credentials cannot be saved to settings and are omitted from the settings response. UNO AUTH/watchdog timing constants are compile-time; only CFG fields can change without recompilation. These limitations are explicit rather than silently implying every setting changes firmware remotely.
15. latency_bench.py computes statistics only from actual external-instrument timestamps. It cannot infer physical light/sound timing from simulator or host event messages. Definitions and acquisition instructions are in TEST_PLAN; no measurement CSV or numbers are fabricated.
16. Keep protects original incident evidence and failed-scan photos; retention also protects active empty-reference calibration images. Historical events/rows remain. Filesystem-backed .jpg/.mp4 media beyond retention are deleted locally, so back up important data and mark Keep first.
17. Only one active session is permitted. An expression-based partial unique index coalesces NULL end_ts to a constant, because a plain unique index on nullable end_ts would allow multiple open rows in SQLite. Existing development databases require a schema migration/recreation to change an old index; fresh installations get the correct index.
18. Development port 8000 was occupied by another process, which was left alone. The verified preview uses 127.0.0.1:8123. The normal scripts retain the requested conventional default port; pass --port to the entry point when needed.
19. Authorization uses a separate whitelist-cache lock, never the database-backed rules lock. REMOVAL dispatch occurs before acquiring the rules lock. Vision caches calibrated slots/references and reloads them on management/calibration changes, so loss of SQLite after startup cannot block an otherwise observable shelf-removal command. Regression tests hold the rules lock and inject a database outage to verify this boundary.
20. After the core 27-test baseline, frontend build, and active/passive UNO compiles passed, optional M10 was added. ZONES_ENABLED defaults false. Enabled zone enforcement creates WARNING incidents for workers lacking an explicit assignment to the slot's zone; unzoned slots are unrestricted. An active worker's removal never causes a zone buzzer. API/UI support zone CRUD and per-person assignment.
21. The initial Arduino CLI downloader failed DNS; a local ignored build toolchain was bootstrapped using official Arduino archives and SHA-256 checks from its package index. Final compiler checks use AVR core 1.8.6 and MFRC522 1.4.12. Nothing was flashed and no hardware result is inferred from compilation.
22. v2 starts from tag v1.0 on branch v2. Baseline on 2026-10-25: 28 tests passed in 46.63 s. The supplied v2 prompt explicitly requests a hardware checkpoint after M2; ledger, multi-session TTLs, strict reconciliation, Telegram and learned/rectified vision remain M3–M8 work, not silently claimed complete.
23. M1 retains v1 simulator/parser snapshots solely for explicit legacy regression tests. Default transport and firmware use protocol 2.0. AUTH uses result codes and n; FB confirms results and the temporary backend adapter mirrors IN/OUT into the old session model. Until M3, a second different badge receives PRM rather than a board BUSY message. The board itself never toggles online sessions. v1 session-lenient shelf tests now dispatch ALARM SHELF_BREACH only while unattended; assertions retain the alarm-isolation guarantee with the new wire command.
24. M1 baseline: 37 tests passed in 40.90 s; frontend builds. Core compile bytes flash/RAM: active reader1 11898/442, passive reader1 12672/459, active reader2 11950/467, passive reader2 12724/484. M2 adds EEPROM/replay and will remeasure all four. Watchdog/EEPROM/multi-reader references checked against Arduino/avr-libc and the official MFRC522 multi-reader example; actual reset causes and shared-SPI electrical behavior still need hardware validation.
25. Dead-man expiry emits PW ESC followed by one ALARM DEADMAN using the shelf pattern; it does not emit duplicate SHELF_BREACH incidents. New PW commands may shorten but never extend an existing deadline. Buttons act on debounced release: short press mutes only, >=1.5 s hold/release acknowledges when enabled. FB measures firmware dispatch-to-output code, not light/acoustic latency; synthetic telemetry is explicitly labeled unmeasured.
26. M2 uses a 500-byte union for upload staging versus the offline ring; WL is refused until replay drains. END validates version/count/CRC and duplicate hashes before EEPROM writes, publishes magic last, and skips a byte-identical valid image. Cache rejection preserves the preceding list. Firmware max global RAM is budgeted at 1100 B; stack remains a separately measured hardware concern.
27. FNV-1a hashes uppercase UID characters, not raw RFID bytes. CRC16-CCITT-FALSE covers version/count and little-endian hash/flag bytes. Immutable shared JSON/header vectors are checked by Python and compiled into the real EEPROM test sketch using the main firmware's shared protocol_core.h. C++ execution remains a physical test; compilation alone is not claimed as a vector runtime result.
28. The boot id uses two alternating counter/complement slots at EEPROM 1008–1023; a torn new counter write retains the other valid slot. Whitelist data ends by address 505, scratch tests use 900–903. Offline RAM logs/sessions cannot survive reset/power loss, including UNO serial auto-reset. The real conformance fixture pauses HB without closing the port, then runs the actual backend commit/dedup service against a separate hardware-replay DB.
29. Offline cache supports 100 entries, 8 local badge identities and 16 pending events. Full ring refuses new operations rather than overwriting. Recent badge (<30 s) wins item attribution, else a sole badge, else NSS. Permission failures PRM do not increment gate failures. M2 automatic cache synchronization contains active badges at L1 only because actual item-tag/clearance/ledger schema belongs to M3; explicit two-tag hardware fixtures validate board level logic without claiming online item issuing exists.
30. Replay commits a composite-key (BOARD_ID, boot id, event id) row and one OFFLINE_EVENT before OFFOK. Repeated deliveries are idempotent; different immutable payload with the same identity is rejected. Failure to commit sends no ACK. BOARD_ID must change for a new/fully erased board when preserving old history. OFF age gives estimated wall time, not synchronized physical timing. Replay does not yet construct multi-session or inventory loan state.
31. Whitelist synchronization is a separate low-priority worker paced at 40 ms per line, with bounded retries/status and an explicit retry endpoint. Its callbacks never perform DB/camera work on the serial reader. AUTH remains direct from RAM. Revocation is only effective offline after CURRENT/WLOK; failed uploads intentionally retain old EEPROM entries.
32. M2 maintains an explicit checkpoint banner and the old online single-worker/session-lenient policy until M3/M4. A second active badge gets PRM from the temporary PC adapter. Declared/observed mismatch protection is not claimed implemented at this stop. Full new R-UI and reveal marker numbering/rectification are deferred to M6/M8; M2 adds only diagnostics and compatibility/cache controls.
33. Official watchdog startup reference verified at https://avrdudes.github.io/avr-libc/avr-libc-user-manual/group__avr__watchdog.html and EEPROM.update source at https://github.com/arduino/ArduinoCore-avr/blob/master/libraries/EEPROM/src/EEPROM.h . The MFRC522 multi-reader example remains the wiring/polling reference, not proof of reliable shared-SPI behavior on every module. DevRelay research was retried for the v2 task but remains unavailable without an account connection; no citations were invented.
34. Runtime simulation persists its 1024-byte EEPROM image under DATA_DIR/sim-eeprom.bin, including journaled boot ids, so backend restarts do not silently reset the simulated cache/dedup epoch. A separate atomic-file writer drains after serial workers stop; simulated disk I/O cannot stall AUTH or timer threads. This does not make offline RAM logs persistent and is not a real EEPROM wear/power-failure test.
35. A successfully committed replacement cache also removes revoked remembered offline badges and applies changed levels to retained badges. Keeping a stale remembered permission after CURRENT would undermine revocation. The firmware and simulator implement the same refresh; a regression checks downgrade and removal.
36. Final M2 verification: 49 tests passed in 46.82 s; locked frontend installation/build and dependency checks passed. Final flash/global RAM bytes: reader1 active 15946/1010, reader1 passive 16720/1027, reader2 active 16008/1035, reader2 passive 16782/1052. All six test sketches compile. See V2_VERIFICATION.md; physical measurements remain blank.
37. The user resumed operational software on 2026-10-27 and supplied reader #2 SS D4/RST D5, superseding M2's stop and D5/D3 map. Reader #1 is badges; #2 is item tags. Shared SPI/LED/buzzer pins stay unchanged. The absent button is disabled (optional A0). Firmware 2.1 identifies this profile while retaining wire protocol 2.0; strict mode rejects old M2 firmware.
38. Gate failure counting now belongs only to rd=0, including timeouts. Item-reader denials do not trigger GATE_3_FAIL. The old pattern test now counts on rd=0 and retains per-reader debounce coverage; new integration coverage checks item non-escalation. Two-reader offline mode enforces roles; one-reader offline fixtures retain their older registry behavior.
39. Strict mode caches four TTL sessions, attribution and item/permission/loan state. FB confirms mutations before SQL; command dispatch precedes queued durability. A separate timer thread contains no SQL/camera/provider calls. A failed durable head remains queued in order and health exposes failure. legacy_engine/session_lenient retains v1 regression behavior; ten old threaded scenarios are supplemented by a strict operational table.
40. Additive schema version 3 preserves history. Cross-table SQLite triggers enforce badge/item UID exclusivity during concurrent API writes. Transactions/reconciliations have idempotency tokens; a reconciliation and incident commit together. Provider/evidence exceptions cannot erase a verdict. Overdue warnings use item/due identity across restart. A clean hardware DATA_DIR and private backup are human steps, not automated deletion.
41. One confirmed ISSUE grants one short-lived removal token. PW tracks the earliest unresolved deadline; new removals cannot extend it. Resolving the earliest explicitly cancels/rearms for the next. Denied/unattended removal sends ALARM first. Replacing an undeclared box does not erase its pending event. Return/overdue exceptions warn without a buzzer. Unhealthy/unknown camera observations are not proof of theft.
42. GATE_PHOTO_POLICY=third_failure saves laptop photos only on GATE_3_FAIL while retaining RAM preview. First/second failures are logged without photos. Shelf incidents use phone evidence, preferring detection-time frames held in bounded RAM during grace. Clips resample available history and can repeat frames; unavailable cameras yield no-photo diagnostics instead of blocking the alarm.
43. Four non-collinear learned anchors define projective homography; exactly three yield affine fallback. Invalid/insufficient learned anchors suspend classification. The operator learns resting positions, refines ROIs and validates reveal markers/empty references. Items 0–19 and reveal 20–39 are distinct; marker API test 39 was intentionally changed to accept it and reject 50. Synthetic pose moves the whole plane.
44. Calibration pause suppresses new shelf rules but preserves RFID and armed deadlines; unresolved removals prevent pausing. Resume restarts voting. UI adds sessions/expiry, levels/tags, ledger/CSV, calibration controls and reconciliation history; Ledger is a separate component. A full aesthetic UI rewrite and optional person detector/LCD/ultrasonic are outside this circuit.
45. WhatsApp remains default: complete private configuration, exact public HTTPS base and signed owner inbound refresh the tracked 24-hour window. Partial setup shows FAILED_CONFIGURATION. Telegram is an optional independent queue with multipart JPEG upload and mocked retry/rate-limit tests. No real messages were sent. Official Twilio Sandbox/media/signature and Telegram Bot API references were checked. DevRelay research was attempted but remains unavailable without its account connection; no citations were invented.
46. EEPROM sync now includes badge levels/item minimum levels. OFF records lack reliable holder attribution, so replay remains a deduplicated audit and does not fabricate online loans. Offline levels cannot enforce laptop SQL zones, TTL jobs or camera observation; manual review is documented. Reset still loses volatile logs/sessions.
47. An inventorySystem Vite process held Rollup and caused npm ci EPERM. Only that identified preview was stopped; install/build then passed. Other Python/Node apps were left alone. scripts/dev.ps1 now accepts -Port for a smoke test or occupied default port.
48. Final operational validation: 67 tests passed in 50.44 s (one dependency deprecation warning), all 31 scenario checks passed, locked frontend install/build passed, four firmware variants and six sketches compiled within budgets. A built-dashboard browser/HTTP smoke with isolated ignored data verified current firmware, two synthetic cameras, cache CURRENT, badge entry, item ISSUE and MATCHED removal. Names, dates and physical reader numbers are shown in Ledger. The temporary backend/tab were stopped. No physical upload or provider message was performed; OPERATIONAL_VERIFICATION.md distinguishes these boundaries.
